# Building physics-ready robot-simulation scenes from a phone scan + detected objects (Blender/bpy, procedural & LLM scene tools, scan-to-sim), as of Oct 2026

Scope note: researched 2026-10-22. Licences were read directly from each repo's LICENSE file on raw.githubusercontent.com (main/master branch) unless stated otherwise. "Commercial OK?" refers to the licence text only, not legal advice. Older (pre-2025) results are marked "(older)".

## 1. Blender as a headless scene builder: bpy, performance, Docker/GPU, USD quality, and GPL implications for a SaaS

### Takeaway
Blender can be driven fully headless (`blender -b --python` or the `bpy` pip wheel, now 5.2.x on Python 3.13 only), and its USD exporter handles meshes, materials, units (metersPerUnit), axis conversion, instancing and custom properties, but it does NOT author UsdPhysics (no colliders, rigid bodies, mass); physics must be added afterwards with a `USDHook.on_export` callback or a separate `pxr` post-pass. GPL does not bite a server-side SaaS that only returns outputs: running modified GPL code on a server is not "conveying", and Blender's outputs are the user's property; only distributed Blender builds or published bpy scripts carry GPL obligations.

### Cited Findings
**Licence / GPL**

- Blender says the GPL "requires that such scripts (if published) are being shared under a GPL compliant license"; you may sell scripts, buyers receive them under GPL — [Blender licence page](https://www.blender.org/about/license/)
- The Blender licence page does not directly address server/SaaS use; it offers organisations "feedback on license compliance" — [Blender licence page](https://www.blender.org/about/license/)
- GPL FAQ "UnreleasedMods": a company running a modified GPL program on a web site "does not have to release the modified sources"; this differs only under the AGPL — [GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#UnreleasedMods)
- GPLv3 §0: "Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying." §2: "You may make, run and propagate covered works that you do not convey, without conditions" — [GPLv3 text as shipped in BlenderProc LICENSE](https://github.com/DLR-RM/BlenderProc/blob/main/LICENSE); canonical text at [gnu.org](https://www.gnu.org/licenses/gpl-3.0.html)

- The `bpy` PyPI package itself is declared `GPL-3.0` — [PyPI bpy](https://pypi.org/project/bpy/)

**bpy wheel / headless**
- `bpy` latest is 5.2.2 (2026-09-15), `requires_python ==3.13.*`; the 4.5 LTS line (4.5.14, 2026-09-15) ships cp311 wheels; 4.2 LTS line (4.2.23) also cp311. 5.2.x wheels: macOS arm64, manylinux_2_28 x86_64, win amd64/arm64 (no macOS x86_64 listed); 4.5.x still lists macOS x86_64 — [PyPI bpy JSON](https://pypi.org/pypi/bpy/json)
- "Each Blender release supports one Python version, and the package is only compatible with that version"; versions outside the LTS window are removed from PyPI but kept at download.blender.org/pypi/bpy — [PyPI bpy](https://pypi.org/project/bpy/)
- The current Blender manual is labelled "Blender 5.2 LTS Manual" — [Blender manual USD page](https://docs.blender.org/manual/en/latest/files/import_export/usd.html)
- bpy-module limitations: `importlib.reload` raises; "Only a single .blend file can be edited at a time"; command-line-argument functionality isn't accessible; other Python modules may use the GPU "in a way that prevents Blender/Cycles from accessing the GPU"; Blender's signal handlers are not initialised; it behaves as if `--factory-startup` was passed; otherwise "equivalent to running a script in background-mode". Multiple instances are possible as separate processes (docs suggest `multiprocessing`). Listed use cases include "3D file conversion" and "Automation" — [Blender as a Python Module](https://docs.blender.org/api/current/info_advanced_blender_as_bpy.html)
- Docker: nytimes/rd-blender-docker publishes CPU and GPU Blender images (tags seen stop ~3.3.1, older); a community `bpy` ROCm image (Blender 4.5.1) runs headless on AMD GPUs needing /dev/kfd and /dev/dri — [rd-blender-docker](https://github.com/nytimes/rd-blender-docker); [bpy-rocm](https://hub.docker.com/r/guerrillatechnology/bpy-rocm)
- Headless multi-GPU runs can silently fall back to CPU; fix was scripting each Cycles device's `use` flag (2020 thread, older) — [Blender devtalk](https://devtalk.blender.org/t/solved-2-90-headless-rendering-ignoring-script-selecting-gpus-falls-back-on-the-cpu/16886)
- Community reports: Cycles CUDA/OptiX needs no display; EEVEE historically needed OpenGL/X server; EGL-based headless EEVEE on current versions is unconfirmed — [search summary of blenderartists / snowgoons posts](https://blenderartists.org/t/run-blender-in-a-docker-container/1643868) (secondary, partly 2020)

**USD import/export quality**
- Export options (5.2 manual): **Units** sets stage `metersPerUnit` (custom value allowed); **Convert Orientation** with Forward/Up axis remap (Blender is Z-up, Y-forward); **Instancing** (Experimental) exports duplicates as references; **Triangulate**; materials as **USD Preview Surface Network** and **MaterialX Network**; **Custom Properties** exported under a **Namespace** defaulting to `userProperties`; **Blender Names** written as custom attributes. Import: **Apply Unit Conversion Scale** using stage metersPerUnit; Y-up files get a root rotation; **Scene Instancing** to collection instances — [Blender manual USD](https://docs.blender.org/manual/en/latest/files/import_export/usd.html)
- The manual's export type list is meshes, cameras, lights, hair as curves, volumes, armatures; no physics/rigid-body schema is mentioned; "Blender does not (yet) support exporting invisible objects, USD layers, variants, etc." — [Blender manual USD](https://www.blender.org/manual/en/files/import_export/usd.html)
- Blender 5.0 release notes contain only one USD item (NURBS curve import/export); nothing on physics, units or instancing — [Blender 5.0 Pipeline & I/O notes](https://developer.blender.org/docs/release_notes/5.0/pipeline_io/)
- June 2025 Pipeline & I/O meeting: new ufbx-based FBX importer default in 5.0; Collada fully removed from 5.0 — [devtalk meeting notes](https://devtalk.blender.org/t/2025-06-19-pipeline-i-o-module-meeting/41136)
- 5.3 (in development) notes: USD mesh export writes normals matching Blender's representation — [Blender 5.3 Pipeline & I/O notes](https://developer.blender.org/docs/release_notes/5.3/pipeline_io/)
- `bpy.types.USDHook` callbacks: `on_export(export_context)` runs before the stage is saved, with `get_stage()`, `get_depsgraph()`, `get_prim_map()` (USD prim path → Blender IDs); also `on_material_export`, `on_import`, `material_import_poll`/`on_material_import` — [USDHook API](https://docs.blender.org/api/current/bpy.types.USDHook.html)
- NVIDIA's Omniverse Blender connector release notes (Blender 4.2 build, Oct 2024 — older) cover USD export fixes and OmniPBR/OmniGlass, not physics — [Omniverse Blender release notes](https://docs.omniverse.nvidia.com/connect/latest/blender/release-notes.html)

### Inferences
- For a SaaS: running stock or modified Blender/bpy server-side and returning USD/OBJ/renders creates no source-release obligation (GPL, not AGPL). Obligations appear if BrainSNN ships Blender (or a bpy-linked app) to customers (desktop app, on-prem appliance, Docker image given to customers) or publishes bpy scripts — those must be GPL-compatible.
- Cleanest arms-length architecture: keep the core World Builder (proprietary) separate, invoke Blender as a subprocess/worker (`blender -b --python job.py -- args`) exchanging files (JSON scene spec in, USD/GLB out). Importing `bpy` inside the proprietary server process is a shared address space and is the riskier pattern if that code is ever distributed; the bpy-module approach is fine for internal/SaaS use only.
- Because Blender's USD export lacks UsdPhysics, a Blender layer is mainly useful for geometry ops (booleans, remesh/decimate, UVs, materials, rendering previews, procedural generators like Infinigen). Physics authoring (CollisionAPI/RigidBodyAPI/MassAPI/PhysicsScene) is better done in `pxr` (usd-core) either inside `USDHook.on_export` or as a post-pass — so the physics authoring code need not depend on Blender at all.
- Pin a Blender LTS (4.5 on Python 3.11, or 5.2 on Python 3.13) and its bpy wheel; the one-Python-version constraint makes bpy hard to co-install with other ML stacks, which favours a dedicated Blender container.

### Gaps
- No official Blender Foundation statement specifically on SaaS/server use was found; the analysis rests on the GPL text and FSF FAQ.
- Could not confirm whether Blender 5.1/5.2 added any UsdPhysics import/export (5.0 notes show none; 5.1/5.2 notes not read). Treat "no physics in Blender USD" as true for 5.0 and likely for 5.2, but verify.
- No current benchmark of headless bpy throughput (scene build/export seconds) was found; EEVEE headless (EGL) status on 4.5/5.2 unverified.

## 2. Procedural / LLM scene generation and 2025–2026 scan-to-sim systems: what they do, I/O, accuracy, and licences (code vs assets)

### Takeaway
Most layout/generation systems (ProcTHOR, Holodeck, LayoutGPT, I-Design, LayoutVLM, Infinigen) create plausible but invented scenes; only a few are conditioned on a real scan (Phone2Proc on Apple RoomPlan, Digital Cousins/ACDC from one RGB image, MetaScenes/Scan2Sim, SpatialLM from point clouds, OpenReal2Sim, GaussGym). Code licences are mostly permissive (MIT/Apache/BSD), but the asset libraries they rely on are often non-commercial (3D-FRONT/3D-FUTURE, PartNet-Mobility, part of Objaverse, Scan2CAD annotations, SceneScript). Infinigen (BSD-3, fully procedural) and permissively licensed Objaverse subsets are the main commercially safe content sources.

### Inferences
- Closest match to BrainSNN's product (scan → floor map + detected boxes → sim): Phone2Proc (layout-conditioned procedural fill; Apache-2.0, but AI2-THOR/Unity output), ACDC (detected objects → retrieved assets scaled to point-cloud extents), SpatialLM (point cloud → walls/doors/OBBs), and MetaScenes/Scan2Sim (scan object → asset replacement). None outputs Isaac-ready UsdPhysics end-to-end from a phone scan with a commercial-clean asset base; BrainSNN would assemble its own pipeline.
- Commercially safe asset sources: Infinigen procedural assets (BSD-3), Objaverse objects filtered to CC0/CC-BY (attribution required; CC-BY-SA adds share-alike), TRELLIS-generated meshes (MIT code; output rights per model terms). Avoid shipping 3D-FRONT/3D-FUTURE, PartNet-Mobility, ShapeNet, Scan2CAD annotations, SceneScript, BEHAVIOR assets (terms not verified) in a commercial product.
- ACDC's evidence (twin 25% vs cousin 90% real success) argues that exact geometric replicas are less important for policy robustness than distributions of plausible variants — but for navigation/planning maps, measured walls and obstacle footprints still matter more than object identity.

## 3. Fitting geometry to scans: primitives, OBBs, CAD retrieval/alignment, mesh reconstruction, convex decomposition, and accuracy

### Takeaway
A robust, licence-clean stack exists: Open3D (MIT) for RANSAC planes, DBSCAN clustering, oriented bounding boxes, Poisson and TSDF reconstruction; trimesh (MIT); CoACD (MIT) or V-HACD (BSD-3) for convex decomposition. Retrieval-and-scale (ACDC-style) gets centimetre-to-decimetre placement (≈4–16 cm centre error, bbox IoU ≈0.6–0.75 in sim-to-sim tests); exact CAD alignment (Scan2CAD) is research-grade with non-commercial annotations. For physics, measured primitives (boxes/cylinders) are both the most honest and the fastest colliders.

### Cited Findings
- Open3D (MIT, © 2018–2026) — [LICENSE](https://github.com/isl-org/Open3D); "supports segmentation of geometric primitives from point clouds using RANSAC... use segment_plane" (args incl. `distance_threshold`, `ransac_n`); DBSCAN clustering; bounding volumes incl. `AxisAlignedBoundingBox` and `OrientedBoundingBox` — [Open3D point cloud tutorial](https://www.open3d.org/docs/release/tutorial/geometry/pointcloud.html)
- Open3D Poisson (`create_from_point_cloud_poisson`, wrapper of Kazhdan): "will also create triangles in areas of low point density, and even extrapolates into some areas"; returns per-vertex densities usable to trim — [Open3D surface reconstruction](https://www.open3d.org/docs/release/tutorial/geometry/surface_reconstruction.html)
- Open3D TSDF: `ScalableTSDFVolume` recommended for larger scenes; example `voxel_length = 4.0/512.0` = 7.8125 mm — [Open3D RGBD integration](https://www.open3d.org/docs/release/tutorial/pipelines/rgbd_integration.html)
- trimesh — MIT — [LICENSE](https://github.com/mikedh/trimesh)
- CoACD (SIGGRAPH 2022) — MIT; `pip install coacd`, `coacd.run_coacd(mesh)`; concavity threshold `-t` (0.01–1, default 0.05); `-rm` interprets threshold in metres for real-scale meshes; manifold preprocessing; `-c` max hulls; per-hull vertex cap (default 256); `-am box` option; `--split` needed for MuJoCo/Bullet "because a single merged file collapses to one convex shape" — [CoACD README](https://github.com/SarahWeiii/CoACD)
- V-HACD — BSD-3-Clause — [LICENSE](https://github.com/kmammou/v-hacd); obj2mjcf (MIT) creates MuJoCo collision meshes by V-HACD decomposition of OBJ — [obj2mjcf](https://github.com/kevinzakka/obj2mjcf), [PyPI](https://pypi.org/project/obj2mjcf/0.0.17)
- Scan2CAD (CVPR 2019, older): 9-DoF CAD alignment to ScanNet scans; 1,506 scans, 97,607 keypoint pairs, 14,225 ShapeNet models; reports +21.39% over handcrafted/CNN baselines (relative) — [arXiv 1811.11187](https://arxiv.org/abs/1811.11187); annotation licence CC BY-NC-SA 3.0 — [LICENSE](https://github.com/skanti/Scan2CAD)
- ACDC-style retrieve-and-scale accuracy (sim-to-sim): centre L2 4.15–15.67 cm, orientation 0.03–0.12 rad, 3D bbox IoU 0.59–0.74; scale taken from point-cloud extents, orientation from DINOv2 optionally refined by a z-aligned minimum bounding box; DBSCAN removes noise; objects lifted to remove penetration — [ACDC HTML](https://arxiv.org/html/2410.07408v3)
- Isaac Sim: convex decomposition can "significantly slow down runtime performance" and be "not very accurate to the mesh boundaries"; enabling shrink-wrap improved accuracy (forum, user reports) — [NVIDIA forum](https://forums.developer.nvidia.com/t/how-to-programmatically-apply-convex-decomposition-with-shrink-wrap-to-match-isaac-sim-ui-defaults/310338)
- MuJoCo performance guidance: prefer "replacing expensive collision tests (e.g. mesh-mesh) with cheaper primitive-primitive collisions"; "If replacing collision meshes with primitives is not feasible, decimate the meshes as much as possible" (tools: trimesh, Blender, MeshLab, CoACD) — [MuJoCo modeling guide](https://mujoco.readthedocs.io/en/latest/modeling.html)
- Isaac Sim: bounding cube and sphere are "the cheapest collisions possible"; "Fewer convex hulls typically results in higher performance" — [Isaac Sim simulation fundamentals](https://docs.isaacsim.omniverse.nvidia.com/latest/physics/simulation_fundamentals.html)

### Inferences
- Recommended fitting ladder per detected object: (1) measured OBB from the object's segmented points (Open3D OBB, gravity-aligned / yaw-only, after DBSCAN) → box collider with measured dims; (2) optional retrieved/generated visual mesh scaled to that OBB (ACDC-style), keeping the OBB as collider or CoACD hulls of the scaled mesh; (3) walls/floor from RANSAC planes, extruded to thin boxes (static colliders) rather than Poisson meshes.
- Poisson fills holes by extrapolation, so Poisson surfaces should be labelled "inferred" and not used as static colliders where no points support them; TSDF meshes only cover observed space and are more honest for "measured" collision.
- Expected accuracy: object dimensions are bounded by scan metric scale error plus segmentation bleed and occlusion (backs/undersides unseen → OBB underestimates depth against walls). ACDC's ~4–16 cm placement error is a realistic order-of-magnitude for retrieval-based object placement.

### Gaps
- No source found giving measured-vs-true dimension error for phone (ARKit/LiDAR or monocular) scans of furniture; this is likely covered by the metric-scale research thread.
- Absolute Scan2CAD alignment accuracy and newer (2024–2026) CAD-retrieval benchmarks (e.g., ROCA/DiffCAD-type methods) not collected.
- No quantitative V-HACD vs CoACD comparison retrieved (CoACD README makes no V-HACD comparison).

## 4. Keeping provenance honest (measured vs inferred vs generated) and sim-to-real risk from hallucinated geometry

### Takeaway
No standard USD schema for "measured/inferred/generated" provenance was found; the practical mechanism is per-prim custom attributes (Blender exports custom properties under a `userProperties` namespace; `pxr` can author any namespaced attribute). The literature shows that generated fills and splat-only scenes are where sim-to-real breaks: splats carry no collision, Poisson extrapolates, VLM-driven real2sim still fails ~half of episodes, and retrieval methods' real-world accuracy is often only judged qualitatively.

### Cited Findings
- Blender USD export writes custom properties into a namespace (default `userProperties`) and can write original Blender names as attributes — [Blender manual USD](https://docs.blender.org/manual/en/latest/files/import_export/usd.html)
- `USDHook.on_export` exposes the stage and a prim map (USD prim path → Blender IDs), enabling per-prim metadata authoring at export — [USDHook API](https://docs.blender.org/api/current/bpy.types.USDHook.html)
- Poisson reconstruction "even extrapolates into some areas"; density output lets you identify low-support regions — [Open3D surface reconstruction](https://www.open3d.org/docs/release/tutorial/geometry/surface_reconstruction.html)
- Gaussian-splat scenes contain only visual geometry; tutorials add a ground plane for physics; Places Library pairs splats with an aligned collision mesh — [Radiance Fields](https://radiancefields.com/niantic-spatial-launches-places-library); a user's nvblox mesh came in "nearly 100 times scaled down" vs the Gaussians and misaligned — [NVIDIA forum](https://forums.developer.nvidia.com/t/loading-usdz-files-from-nurec-pipeline-into-isaac-sim-does-not-load-mesh-file/352914)
- ACDC real-to-sim results were qualitative only "since no ground-truth poses or twins exist for real objects"; limitation: asset dataset "does not densely cover real-world object distributions" and inherits failure modes of pretrained models — [ACDC HTML](https://arxiv.org/html/2410.07408v3)
- Twin-only policy: 100% sim → 25% real; cousin policy 94% → 90% (cabinet opening) — [ACDC HTML](https://arxiv.org/html/2410.07408v3)
- Agentic Real2Sim: VLMs make "bounded decisions" while deterministic tools do perception/simulation; still 44/100 failed episode twins with the best backend — [HF papers 2607.19190](https://huggingface.co/papers/2607.19190)
- Infinigen whole-scene export without `solve_state.json` makes all objects static colliders (physical relations come from the solver state, not geometry) — [Infinigen docs](https://infinigen.cs.princeton.edu/docs/latest/ExportingToSimulators.html)

### Inferences
- Adopt a three-level label on every prim and every collider, e.g. `brainsnn:provenance = "measured" | "inferred" | "generated"` plus `brainsnn:source` (scan id, detector + confidence, asset id + licence) and `brainsnn:dimsSource` ("scan_obb" vs "asset_default" vs "vlm_estimate"). Keep this in USD custom attributes and mirror it in the 2D World map (e.g., hatch inferred/unknown zones).
- Rule of thumb: colliders should come only from measured geometry (or measured OBBs); generated/retrieved meshes are visual-only unless their bounding box was fitted to measured points. Unknown/unscanned zones should become explicit "unknown" volumes (or conservative blocking boxes for navigation), never silently filled with plausible furniture.
- Keep the Blender/generative layer as a "dressing" pass on top of a measured skeleton (floor, walls, obstacle OBBs), so the planner-relevant geometry is identical with or without Blender.
- Provide a "cousins" mode (randomised variants of generated parts) separately from the "twin" export, labelled as such, following ACDC's evidence that variation helps transfer.

### Gaps
- No published standard (OpenUSD, SimReady, ASWF) for provenance/uncertainty labels on reconstructed geometry was found in this pass.
- No quantitative study found that isolates sim-to-real loss caused specifically by hallucinated (generated) geometry in navigation scenes.

## 5. Export path to Isaac Sim / Isaac Lab (OpenUSD + UsdPhysics) and MuJoCo (MJCF), with pitfalls

### Takeaway
Author the stage explicitly in metres and Z-up (`metersPerUnit=1`, `upAxis="Z"`, because unauthored metersPerUnit falls back to 0.01 = centimetres), add a PhysicsScene, put UsdPhysics CollisionAPI on static geometry (walls/floor/furniture), and RigidBodyAPI + MassAPI only on movable objects using convexHull/convexDecomposition/primitive colliders (triangle meshes fall back to convex hull on dynamic bodies). For MuJoCo, every mesh geom is collided as its convex hull, so non-convex objects must be split (CoACD `--split`) or represented by primitive geoms; the MuJoCo OpenUSD `mjcPhysics` schema now exists to carry MuJoCo-specific collision settings in USD.

### Cited Findings
**OpenUSD / UsdPhysics**
- If `metersPerUnit` is unauthored "we fall back to the value [UsdGeomLinearUnits::centimeters], i.e. 0.01"; linear units are stage-wide like upAxis — [OpenUSD UsdGeom linear units](https://openusd.org/release/api/group___usd_geom_linear_units__group.html)
- UsdPhysics: MeshCollisionAPI approximation choices = none ("generally lowest performance"), simplified mesh, set of convex hulls, single convex hull, bounding box, bounding sphere; unsupported approximations should fall back to "the most similar supported option"; CollisionAPI on UsdGeomGprim, prims without a rigid body are static colliders; MassAPI separate from RigidBodyAPI and optional when mass derives from geometry/density; PhysicsScene gravity defaults to opposite the stage up axis with Earth magnitude; distance units follow metersPerUnit, mass via kilogramsPerUnit; plane colliders must not be on non-kinematic rigid bodies — [OpenUSD UsdPhysics overview](https://openusd.org/release/api/usd_physics_page_front.html)

**Isaac Sim / Isaac Lab**
- Isaac Sim docs (page updated Oct 14, 2026; 6.x): default mesh approximation is convex hull; convex decomposition "at a small expense"; bounding cube/sphere cheapest; sphere approximation available; triangle mesh and mesh simplification "not supported by rigid bodies and fall back to convex hull"; SDF Mesh allows triangle-mesh geometry on a rigid body; static colliders = collider without rigid body; Physics Scene default 60 steps/s; contact/rest offset trade-offs (large contact offset = more constraints; small = jitter/tunnelling); CCD must be enabled on scene and body — [Isaac Sim simulation fundamentals](https://docs.isaacsim.omniverse.nvidia.com/latest/physics/simulation_fundamentals.html)
- Forum: "triangle mesh collision (approximation None/MeshSimplification) cannot be a part of a dynamic body, falling back to convexHull" — [NVIDIA forum](https://forums.developer.nvidia.com/t/collider-and-rigid-body-preset-error-physicsusd-parse-collision-triangle-mesh-collision/244203/9)
- Units pitfalls: per-layer metersPerUnit differences make referenced assets appear 100× too large/small — [NVIDIA forum](https://forums.developer.nvidia.com/t/there-are-different-meters-per-unit-for-different-layer-in-one-stage/217397); changing stage meters-per-unit can desynchronise PhysX from visuals — [NVIDIA forum](https://forums.developer.nvidia.com/t/changing-meters-per-unit-breaks-physx/334492); Isaac Sim's Metrics Assembler auto-converts distance/mass/up-axis on referenced assets but users report extra PhysX work still needed — [Isaac Sim OpenUSD fundamentals](https://docs.omniverse.nvidia.com/isaacsim/latest/open_usd.html) (via search summary; forum-based caveats)
- Isaac Sim repo: Apache-2.0 for the open code, but "Building or using the software requires additional components licenced under other terms" (Omniverse Kit SDK, 3D models, textures) — [IsaacSim LICENSE](https://github.com/isaac-sim/IsaacSim); Isaac Lab: BSD-3-Clause — [IsaacLab LICENSE](https://github.com/isaac-sim/IsaacLab)
- Infinigen's own Isaac path: export USDC with `--omniverse` flag, then a script that reads `solve_state.json` for physical relations — [Infinigen docs](https://infinigen.cs.princeton.edu/docs/latest/ExportingToSimulators.html)

**MuJoCo / MJCF**
- MuJoCo (Apache-2.0) — [LICENSE](https://github.com/google-deepmind/mujoco); mesh "collision detection works with the convex hull of the mesh"; `maxhullvert` limits hull vertices (via qhull); mesh inertia option `convex` — [MuJoCo XML reference](https://mujoco.readthedocs.io/en/latest/XMLreference.html); mesh geoms "are convexified for collision purposes" (rigid flex is the non-convex alternative) — [MuJoCo modeling guide](https://mujoco.readthedocs.io/en/latest/modeling.html)
- Contact stability: solref `timeconst` "should be at least two times larger than the simulation time step"; defaults solref "0.02 1" — [MuJoCo modeling guide](https://mujoco.readthedocs.io/en/latest/modeling.html)
- MuJoCo OpenUSD `mjcPhysics` schema: `MjcMeshCollisionAPI` on UsdGeom.Mesh with `mjc:inertia` (legacy/convex/exact/shell) and `mjc:maxhullvert`; meshes with both UsdPhysics.MeshCollisionAPI and MjcCollisionAPI must set `physics:approximation = convexHull`; an MJCF-to-USD converter writes convex-hull collision geoms — [NVIDIA SimReady Foundation MUJOCO.COL.002](https://nvidia.github.io/simready-foundation/latest/capabilities/physics_bodies/physics_rigid_bodies/requirements/mujoco-mesh-collision-api.html)
- Newton physics engine — Apache-2.0 — [newton LICENSE](https://github.com/newton-physics/newton)
- A single convex hull around a whole object "will prevent the robot from interacting with any meaningful features"; model as sub-parts — [ros2_control MuJoCo modeling tips](https://control.ros.org/kilted/doc/mujoco_ros2_control/mujoco_ros2_control/docs/modeling_tips.html)

### Inferences
- Minimal correct Isaac export from the existing box-proxy exporter: set `metersPerUnit=1.0`, `upAxis=Z`, `kilogramsPerUnit=1.0` explicitly; add `/World/PhysicsScene`; walls/floor/large furniture = `UsdGeom.Cube` (scaled) + CollisionAPI, no rigid body; movable objects = Xform with RigidBodyAPI + MassAPI (mass estimate labelled "inferred") and a box or convexHull collider; visual meshes as separate non-colliding children; reference external assets only after normalising their units/up-axis.
- For MuJoCo, generating MJCF directly from the same scene spec (boxes as `<geom type="box" size=half-extents>`, static bodies as worldbody geoms, CoACD-split meshes as multiple geoms) is simpler and more reliable than converting USD; note MuJoCo box `size` is half-extents (standard MJCF convention — verify in docs).
- Biggest practical pitfalls to test automatically: unauthored metersPerUnit (→ 100× scale), Y-up assets from Blender/glTF without orientation conversion, triangle-mesh colliders on dynamic bodies, single convex hull for concave furniture (tables/shelves become solid blocks — fine for navigation, wrong for manipulation), and splat/visual layers without aligned colliders.

### Gaps
- Isaac Lab-specific import utilities (e.g., mesh/USD converter configs) and Isaac Sim 6.x asset-structure requirements were not read in detail.
- Whether MuJoCo's own release now imports USD with UsdPhysics/mjcPhysics natively (vs via Newton or converters) was not confirmed from MuJoCo docs.
- MJCF box half-extent convention stated from general knowledge, not re-verified in this pass.
